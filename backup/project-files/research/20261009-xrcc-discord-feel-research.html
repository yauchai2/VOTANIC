Discord 咁有「地方感」,但 XRCC 唔好變社交 App

Alan 想 XRCC 有 Discord 嗰種活、有身份感、唔悶嘅感覺。呢份報告拆解 Discord 點解成功,對照 Linear、Arc、Figma、Raycast、Duolingo、Slack,再落返 XRCC 現有畫面,講邊啲可以借、邊啲唔應該借。

結論

Discord 嘅感覺,主要來自五樣嘢

佢令你覺得自己「身處一個地方,而且有人喺度」,而唔係「用緊一個工具」。

1 · 地方,唔係頁面

左邊 server、中間 channel、右邊人,位置永遠唔變,所以用幾耐都唔迷路。Judgement

2 · 到處都有一粒「活」嘅訊號

狀態點、朋友而家做緊乜、誰喺語音房。細,但令介面似有生命。Fact

3 · 身份可以自己揀

個人檔案顏色、簡介、自訂狀態、server 圖示。你嘅位有你嘅味。Fact

4 · 低門檻、非正式做預設

入語音房唔使約人,正式活動(Stage)先加結構。Fact

5 · 核心控件規矩,邊位先放玩味

個性集中喺品牌、onboarding、emoji、空狀態,導航同設定仍然傳統清楚。Judgement

對 XRCC 嘅建議方向:「Studio feel」

XRCC 係創作者工具,唔係聊天室。所以唔抄 channel / 訊息流,而係抄佢嘅地方感、presence、身份感、文案聲線。落到 XRCC 就係:Launcher 變成有穩定位置嘅「工作室」,裝置同連線用 presence 點顯示「誰/咩喺度、準備好未」,項目有自己嘅面孔同「最近發生咩」,每個動作回應得似真人。

最值得即刻試嘅三樣(詳見 下一步):Launcher rail 嘅狀態點、「Nearby」裝置區、全 UI 嘅文案聲線統一。

Discord 解構

Discord 點解成功:九個鏡頭

每個鏡頭先講公開事實,再講我嘅判斷。冇來源嘅「三欄結構、Quick Switcher」呢類眾所周知嘅產品行為,我標為 Judgement(一般產品知識,未逐項引用)。

① 空間記憶

Fact Discord 2023 年重做手機版時,試過橫向 dock,但保留 server 垂直靠左,因為好多用戶要頻繁切換多個 server,垂直欄一次顯示最多。同年 overlay 重做亦沿用桌面版嘅慣例(垂直 server 列)減少重新學習。

Judgement 結構穩定令用家建立「肌肉記憶」。呢種穩定本身就係親切感嘅來源。XRCC 嘅 Launcher 已經有左 rail,值得守住位置唔變。

② Presence

Fact 標準狀態有 Online / Idle / Do Not Disturb / Invisible,可加自訂文字同 emoji,並揀幾耐後自動清除。手機版 Messages 頂部有區塊顯示朋友而家做緊乜,方便直接加入。

Judgement 重點唔係「社交」,而係一粒點 + 一句話就令介面有生命,同埋降低「加入」嘅成本。XRCC 嘅裝置、連線、下載、測試場次都係天然嘅 presence 資料。

③ 低門檻入場

Fact 語音房可以隨時入出,唔使打電話或邀請;Stage Channel 係疫情期間觀察到新行為後,為有主持、有講者嘅活動而加,而且被視為新用戶進入社群嘅入口。

Judgement 「非正式做預設,結構做選項」同 XRCC 嘅「zero-code、漸進披露」同一方向,例如 Data Analytics 預設 Protected 路徑,External 先係進階。

④ 身份表達

Fact 個人檔案可自訂簡介(190 字內)同顏色,付費用戶有動態 banner;2021 年 rebrand 令 blurple 更亮更飽和,目標係更大膽同玩味。

Judgement 身份唔一定係頭像。對 XRCC 嚟講,項目先係創作者嘅「身份載體」:封面、顏色、最近一次玩咗咩。

⑤ 密度與暖度

Judgement Discord 列表行密而細,但有大量圓形頭像、emoji 同顏色令畫面唔冷。XRCC 已經有類似特質(縮圖主導、橙色小點綴),問題只係部分畫面(例如 table 型、純灰兩行字空狀態)退回咗「工具味」。

⑥ 共同語言

Fact 自訂 emoji、貼圖、soundboard 令每個 server 有自己嘅內部笑話。(來源多為愛好者文章,證據弱。)

Judgement XRCC 唔需要 soundboard。可借嘅係術語同吉祥物表情:章魚太空人已經存在,可以成為「共同語言」嘅一部分。

⑦ Onboarding

Fact Community Onboarding 要新成員喺發言前完成幾條問題,答案決定佢見到嘅 channel 同 role;問題陳述係新人容易被各社群自訂嘅驗證搞到混亂或離開。Discord 官方文章冇公佈量化成效。

Judgement 原理可用:用幾條簡單問題換一個量身嘅起點。XRCC 已有 Wizard(P8),可以加「你想做咩?」分流,但唔好強制。

⑧ 品牌聲線

Fact 2021 rebrand 報道:Clyde 加咗多種表情,Wumpus 出現喺現實場景,方向係「友善、玩味」。我搵唔到 Discord 官方嘅 UI 文案準則,呢部分只可作旁證。

Judgement 個性集中喺邊緣位(onboarding、空狀態、成功時刻),而核心動作按鈕仍然直白。

⑨ 複雜度代價

Fact Discord 產品經理公開講:手機版要重組,因為 app 能做嘅嘢「exponentially」增加;2025 年桌面外觀更新後,支援論壇有用戶投訴 server 圖示變細、難認。

Judgement 呢個係警號:Discord 嘅「好玩」會隨功能增加變成「亂」。XRCC 有約 600 個行為節點同 30 多類別,更加要靠結構而唔係靠裝飾。

對照產品

其他「有趣而唔悶」嘅產品教咗咩

Linear、Duolingo、Slack 有官方或接近官方來源;Arc、Raycast、Figma 部分來自二手分析,可信度較低,已標明。Spotify、Notion 今次未研究,唔列。

產品公開事實可借嘅一點XRCC 注意
LinearFact 2024 重做 UI 嘅原則:「Don't compete for attention you haven't earned」「Structure should be felt not seen」;側欄調暗、減少邊線、色彩由 98 個變數收斂到 3 個(base / accent / contrast)。導航退後,內容發光;用更少邊線;色彩生成有系統。XRCC 深色底已經收斂。重點係 rail 唔好比主面板搶眼。
ArcFact(二手)用垂直側欄代替橫向 tab,Spaces 分隔不同情境。評論指出「缺少清晰的 why」。「Spaces」= 按情境分組,有各自色彩。XRCC 項目可有個別顏色/封面。警惕:新鮮感唔等於留存。
FigmaFact(二手)有名字、有顏色嘅多人游標,令協作有即時感。Presence 取代明示分享;游標帶個性。只適用多人 / 多裝置連線場景(XRCC 有可選 multiplayer)。Assumption
RaycastFact(二手,偏自動生成摘要)command palette 係核心;紅色強調色「點到即止」。鍵盤優先嘅快速跳轉;單一強調色克制使用。600 個節點 + 多面板,快速跳轉價值高。
DuolingoFact 用 Rive State Machine 令角色按狀態變換動畫;角色(如 Lily)靠鮮明個性成為品牌核心。角色有「狀態」(閒置、思考、慶祝),唔只係靜態插圖。只用喺空狀態/成功時刻,絕對唔可以出現喺高壓操作中。
SlackFact(會議筆記)語音聲線定位「clear, concise, human」,載入訊息用人話,錯誤訊息帶同理心。一把聲線貫穿;邊緣位置多啲人味。XRCC 已有良好文案基礎(見 文案)。
設計原則

八條可以轉化落 XRCC 嘅原則

全部係 Judgement:由上面事實歸納,未經用家驗證。

P1 做「地方」,唔做「頁面」

Launcher 同 Editor 各自有固定嘅位置模型。Rail 位置、次序、名稱唔隨版本亂變。

P2 細而誠實嘅 presence

用一粒點加一句人話,顯示裝置、連線、下載、測試場次嘅真實狀態。唔推斷、唔扮活。

P3 Chrome 退後,內容發光

Rail、標題條用較暗嘅紫調;縮圖、預覽、3D 渲染做主角(借 Linear)。

P4 非正式做預設,結構做選項

新手見到最短路徑;進階設定摺埋(XRCC 已有摺疊摘要行 P14)。

P5 俾項目一個面孔

封面、色調、最近活動。項目就係創作者嘅「server」。

P6 一把聲線

同人講嘢咁:先講發生咩,再講點做。高風險位置(刪除、資料)收斂語氣。

P7 邊緣玩味,核心規矩

空狀態、第一次成功、onboarding 可以玩;刪除、授權、資料匯出要直白。

P8 誠實狀態大過好玩狀態

Data Analytics 已定案「唔推斷」(例如只顯示 "No Finish recorded")。Presence 點必須遵守同一規則。

XRCC 對照

邊啲借、邊啲改、邊啲唔好

背景:XRCC 係 Unity 零代碼 XR 內容創作工具,PC editor(uGUI)、Launcher(UI Toolkit)、XR world-space 面板;用家包括創作者、教學/培訓人員、操作員。來源:項目知識庫。

直接借

  • 穩定的左 rail + 主面板 + 右側狀態區
  • Presence 點 + 一句狀態人話
  • Quick Switcher / command palette(Ctrl+K)
  • 項目「最近活動」一行(類 rich presence)
  • 聲線統一、邊緣位多啲人味
  • 導航退後(Linear 思路)

改造後借

  • Onboarding 問題分流 → 改成可跳過嘅「你想做咩?」
  • 身份表達 → 由用家頭像改成項目封面/色調
  • 多人游標 → 只喺多裝置 / multiplayer 測試時用
  • 角色狀態動畫 → 只喺空狀態同成功時刻
  • Stage 式活動結構 → 對應 Operator / Trainer 場次(需符合 Data Analytics 決策)

唔好借

  • Channel / 訊息流作主體:XRCC 唔係聊天
  • 大量圓形 server 圖示欄:項目數量唔係重點
  • 通知紅點泛濫、付費升級提示
  • 連續登入、徽章等遊戲化壓力
  • 公開顯示用戶狀態:企業/學校環境有私隱顧慮
  • 高飽和 blurple 大面積:XRCC 有自己嘅深紫 + 橙小點綴

XRCC 獨有嘅限制,Discord 冇

  • Fact XR 面板係 world-space,單一 active panel,要大點擊目標;Discord 式細密列表唔可以直接搬去 XR。
  • Fact 客戶包括教學機構與企業項目,信任感同專業感同樣重要;「好玩」唔可以削弱「可靠」。
  • Fact Data Analytics 4.2 已定案:狀態只用 Accepted / Saved locally / Queued / Delivered / Failed,無 pass/fail,無推斷 abandoned。Presence 設計必須在呢個框內。

文案聲線

最平、最快見效:同人講嘢

Judgement XRCC 現有文案已經好(例如 "You're up to date!"),方向係延伸而唔係重寫。UI 文案維持英文為主。以下係風格示範,唔代表已有字串。

空狀態

- No projects found.+ Nothing here yet. Start with a template, or drop in a .ccdata file.
- No devices.+ No headsets nearby. Wake one up and we'll find it.

狀態

- Connected.+ Quest 3 · Ready to launch
- Pending.+ Queued. We'll send it as soon as the connection is back.

成功

- Operation completed.+ Project saved
- Import successful.+ 12 assets are in. Ready when you are.

錯誤

- Something went wrong.+ Couldn't reach Poe. Check your key, then try again.

高風險位置(刪除、授權、資料)保持直白,不加玩笑。

原則:先講發生咩,再講點做;唔責怪;按鈕用動詞;玩味只放喺低風險位置。

風險同取捨

幾個要預先承認嘅問題

風險點解重要減低方法
玩味削弱專業信任客戶包括教學同企業項目。玩味只放邊緣位置;核心動作與資料畫面保持直白。
Presence 誤導「在線」點可能被理解成確認咗嘅狀態。只顯示真實、可驗證嘅狀態;與 Data Analytics 決策對齊。
為 presence 要持續偵測 / 輪詢可能影響效能或電量,亦涉及工程。Assumption 先確認 Launcher 現有偵測能力,再定範圍。
多一個 component 就多一份維護Library 未完成,新增要發佈。Feature 專屬 component 放該 feature 檔案,共用嘅(Presence row、Command palette)才進 Library。
資料隱私顯示「誰做緊乜」係敏感資訊。只顯示本機/本人裝置;唔做跨用戶公開 presence。
XR 不適用小字、細點喺 XR 難點中。本輪只針對 PC;XR 版另行設計大目標版本。
證據偏弱部分來源係二手分析;Discord 官方 UI 準則搵唔到。原則作為假設,用小型測試驗證,唔當定論。

需要驗證嘅假設

  • Assumption 創作者真係想喺 Launcher 見到「最近活動」同 Nearby,而唔係嫌嘈。
  • Assumption Launcher 技術上可以持續偵測裝置同連線狀態(需 Steven / 工程確認)。
  • Assumption PC editor(uGUI)做得到 command palette 同 hover 預覽。
  • Assumption 教學/培訓用戶(Operator、Trainer)接受 presence 式列表,而唔會誤讀。
